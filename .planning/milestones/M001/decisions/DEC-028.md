# 浏览器认证会话、同源部署与 CSRF 防护基线

## 决策问题

CAP-002–005、CAP-106 要求同时支持多会话、只退出当前会话、用户改密后保留当前会话，以及管理员重置密码后失效全部会话。生成与取消又都是浏览器发起的写请求。现在需要确定浏览器如何携带认证凭据、前端与 API 是否同源，以及如何防止凭据泄露、会话固定和 CSRF；这会固定认证 API、部署入口和前端数据访问方式。

## 已确认约束

- M001 是第一方响应式 Web，不提供公共无界面 API、原生客户端、第三方 OAuth/OIDC 或跨站嵌入。
- PostgreSQL 已确认使用 `account_sessions` 保存服务端会话，具备 `token_hash`、`created_at`、`last_seen_at`、`expires_at`，并以删行实现指定会话失效；会话令牌原文不得入库。
- 用户名密码认证、普通退出、自助改密、管理员重置和账号注销具有不同失效范围，不能只依赖客户端自行丢弃凭据。
- OWASP 建议会话标识使用无意义的高熵随机值并把语义保存在服务端；Cookie 应使用 `Secure`、`HttpOnly`、显式 `SameSite`，并建议使用 `__Host-` 前缀。[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- `SameSite` 只是纵深防御。对浏览器写请求仍需验证来源并使用自定义请求头或与会话绑定的 CSRF 令牌；缺失 `Origin`/`Referer` 时推荐拒绝。[OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- 密码按当前安全基线使用 Argon2id 自适应哈希；参数至少达到 OWASP 基线，并在目标部署资源上压测后固化，密码原文和 pepper 不进入数据库或日志。[OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## 可选方向

### 方向 A：同源 API + 服务端不透明 Cookie 会话

- 浏览器只从产品公开源访问页面与 `/api/v1`；生产环境不开放跨源凭据 CORS。静态资源、反向代理和 Go 应用可以是不同内部组件，但浏览器只看到一个 HTTPS origin。
- 登录或注册成功后生成 32 字节 CSPRNG 随机令牌；浏览器只通过 `__Host-ww_session` Cookie 携带原文，属性为 `Secure; HttpOnly; SameSite=Lax; Path=/` 且无 `Domain`；数据库只存带服务端 pepper 的摘要。
- 访客使用独立 `__Host-ww_visitor` 不透明 Cookie，遵循相同安全属性；认证成功必须签发全新的账号会话，不能把访客令牌提升为登录会话。
- 所有非安全方法只接受 `application/json`（SSE 生成请求仍由 POST 发起），校验配置的精确公开 `Origin`、拒绝跨站 `Sec-Fetch-Site`，并要求 `X-CSRF-Token`。令牌由服务端 HMAC 绑定当前账号会话或访客身份，通过同源 bootstrap 响应取得，不写本地存储。
- 学习者会话空闲 7 天、绝对 30 天；管理员会话空闲 30 分钟、绝对 8 小时。服务端同时执行空闲和绝对过期，`last_seen_at` 最多每 5 分钟触碰一次以避免每请求写库。
- 收益：直接满足逐会话撤销和角色授权；凭据不暴露给 JavaScript；同源部署使 Cookie、CSRF、CORS 和 SSE 行为最简单；无需 Redis 或 JWT 撤销表。
- 代价：前端与 API 必须共享浏览器 origin；每个认证请求需要查询 PostgreSQL 会话。
- 风险：若前端出现 XSS，攻击者仍可在页面上下文发请求，因此还必须配合 CSP、输出编码和依赖治理；Cookie 标志不能替代 XSS 防护。
- 适用条件：M001 的第一方 Web 与单实例模块化单体。

### 方向 B：跨源 API + 服务端不透明 Cookie 会话

- 前端与 API 使用不同 origin，API 精确允许一个或多个前端 origin 并启用 credentialed CORS；仍使用服务端不透明 Cookie 和会话表。
- 收益：静态站点和 API 可由不同公开域名独立发布，保留逐会话撤销语义。
- 代价：每个环境都要维护精确 CORS、Cookie、预检、公开 origin 与代理配置；SSE POST、自定义 CSRF 头和错误响应都必须通过跨源预检。
- 风险：配置漂移容易造成凭据被错误放行或生产请求被浏览器拦截；当前没有独立域名部署需求证明这些成本必要。
- 适用条件：部署平台明确无法提供同源反向代理或统一入口。

### 方向 C：短期 JWT Access Token + 轮换 Refresh Token

- JavaScript 以内存 Bearer access token 调用 API，HttpOnly Cookie 保存 refresh token；服务端维护 refresh token 家族和撤销状态，以满足逐会话退出、改密和管理员全失效。
- 收益：适合未来不同域名、原生客户端或第三方 API 调用者；普通请求可少一次会话表查询。
- 代价：需要 access/refresh 双令牌、轮换复用检测、并发刷新、短期撤销延迟和额外数据库状态；前端必须处理刷新竞态。
- 风险：若为实现立即失效而每次仍查撤销状态，会同时承担 JWT 与服务端会话两套复杂度；Bearer token 暴露面也高于 HttpOnly Cookie。
- 适用条件：已经确认存在非浏览器客户端或跨产品 API，而非 M001 的单一第一方 Web。

## 角色建议

`PROPOSED`：选择方向 A。

方向 A 与数据库既有 `account_sessions` 设计和全部会话失效规则直接对齐，并以同一公开 origin 消除不必要的跨域复杂度。角色差异化的服务端空闲/绝对期限在不增加产品入口的情况下兼顾学习者留存与管理员风险；未来确有独立域名时可迁移到方向 B，确有非浏览器调用者时再单独设计方向 C。

## 用户决定

`CONFIRMED`：用户选择方向 A，并确认：

1. 浏览器只通过同一个公开 HTTPS origin 访问页面与 `/api/v1`；M001 不开放跨源凭据 CORS。
2. 账号会话和访客身份都使用 32 字节 CSPRNG 不透明 Cookie；生产 Cookie 使用 `__Host-` 前缀、`Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/` 且不设置 `Domain`，数据库只保存带服务端 pepper 的摘要。
3. 认证成功签发全新的账号会话，不能把访客令牌提升为登录会话；账号和访客原文令牌都不得写入 Web Storage、数据库或日志。
4. 所有浏览器写请求严格校验公开 `Origin`、拒绝跨站 Fetch Metadata，并要求与当前会话或访客身份绑定的 `X-CSRF-Token`；CSRF token 通过同源 bootstrap 取得，不写入持久客户端存储。
5. 学习者会话空闲期限为 7 天、绝对期限为 30 天；管理员会话空闲期限为 30 分钟、绝对期限为 8 小时。两类期限均由服务端执行，`last_seen_at` 最多每 5 分钟更新一次。
6. 密码使用 Argon2id 自适应哈希；参数达到当期 OWASP 基线并在目标部署资源上压测后固化。

## 影响范围

- 确认后固定认证、会话 bootstrap、退出、注册/登录、密码变更、管理员重置、CSRF 错误与部署 origin 契约。
- 方向 A 不要求修改已批准的数据库表；后端需把会话过期、哈希/pepper、Cookie 清除和清理任务写入总体方案。
- 前端架构必须按选定方向处理凭据、CSRF token 和 401 会话过期，不得把会话原文写入 Web Storage。
