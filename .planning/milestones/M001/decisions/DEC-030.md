# Nuxt SSR 前端基座与生产运行时边界

## 决策问题

M001 需要承接 12 个响应式页面、同源 Cookie/CSRF、POST SSE 生成流、只存内存的能力令牌、无刷新语言切换和两类复习状态。现在需要固定 SPA 或 SSR 基座，以及它与既有 Go API 的生产边界。

## 已确认约束

- 用户的技术栈原则是：单页面应用使用 Vue；需要 SSR 时使用 Nuxt。本项目选择 Nuxt + TypeScript + Vite。
- Nuxt 4 默认启用服务端渲染，Nitro 可产出 Node.js、预渲染、Serverless 或 Edge 运行目标；Nuxt 由 Vite builder、Nitro 和 Vue 等核心包组成。[Nuxt 4 Introduction](https://nuxt.com/docs/4.x/getting-started/introduction)
- 当前官方稳定文档版本为 Nuxt 4.5.2；Nuxt 4.5 已使用 Vite 8。Nuxt 5 仍处于开发/兼容预览阶段，不属于“最新稳定版”。[Nuxt 4.5](https://nuxt.com/blog/v4-5) [Nuxt Upgrade Guide](https://nuxt.com/docs/4.x/getting-started/upgrade)
- 后端已经确认浏览器通过同一个公开 HTTPS origin 访问页面与 `/api/v1`，不开放跨源凭据 CORS。Go API 的生成取消注册表和复习 attempt 依赖 M001 单副本语义。
- 生成使用浏览器 `fetch` 发起 POST SSE。生成能力令牌、访客承接令牌、CSRF token 和复习 attempt token 只能留在内存，不得写入 Web Storage；语言切换不能重建正在进行的生成请求。
- 当前项目没有需要兼容的前端业务代码；批准的 HTML/CSS/JS 是交互和视觉原型，不是生产技术基座。

## 可选方向

### 方向 A：Vue 3 + TypeScript + Vite 客户端 SPA

- 使用 Vue Router 管理浏览器路由，Go 同源托管 Vite 静态产物。
- 收益：只有 Go 一个生产运行时；所有流式和能力令牌状态天然只在浏览器存在。
- 代价：公开首页和路由首访需要客户端脚本执行后才得到完整内容；不提供 SSR。
- 风险：后续若补 SSR，需要迁移到 Nuxt 或自行建立服务端渲染体系。
- 适用条件：产品明确不需要 SSR。

### 方向 B：Nuxt 4 + TypeScript + Vite 的运行期 SSR

- 使用 Nuxt 当前稳定版、严格 TypeScript、默认 SSR、Vite builder 和 Nitro Node server preset；Vue 页面在服务端生成初始 HTML，浏览器 hydrate 后接管交互。
- 浏览器继续只访问同一个公开 origin。入口代理把 `/api/v1/**` 直接转发到 Go，其他页面与 `/_nuxt/**` 交给 Nuxt；POST SSE 不经过 Nuxt BFF 二次转发或转换。
- 收益：符合用户指定技术栈；公开首页、登录注册和页面外壳可直接返回 HTML；Nuxt 提供文件路由、按页拆包、类型化配置、SSR 数据能力和统一 Vue 工程约定。
- 代价：生产增加 Nitro/Node 运行时与入口代理；SSR、hydrate、Cookie 透传和客户端专属状态必须有明确边界。
- 风险：若在 SSR 阶段读取私有 API 并把 CSRF 或能力令牌序列化进 payload，或错误缓存用户响应，会扩大泄露与串用户风险；需要禁止私有 API 的共享 SSR 缓存，并让临时令牌保持请求/浏览器内存作用域。
- 适用条件：接受额外运行时，以 SSR 和 Nuxt 工程体系作为长期基座。

### 方向 C：Nuxt 静态生成或全局 `ssr: false`

- 仍使用 Nuxt 工程结构，但只预渲染公开路由或输出传统客户端 SPA。
- 收益：可保留 Nuxt 模块与目录约定，并减少或取消 Node 生产运行时。
- 代价：全局关闭 SSR 会放弃用户选择 Nuxt 的主要理由；动态认证页面仍主要依赖浏览器启动。
- 风险：名义上采用 Nuxt，实际却承担框架成本而没有获得完整 SSR 价值。
- 适用条件：部署环境后续明确不能运行 Nitro，或只需少量静态公开页面。

## 角色建议

原方向 A（React 客户端 SPA）已被用户的技术栈决定取代，不再作为实施依据。

`CONFIRMED`：采用方向 B。M001 使用 Nuxt 4 最新稳定补丁线、TypeScript 与 Vite，保持 Nuxt 默认 SSR；不启用 Nuxt nightly、Nuxt 5 `future.compatibilityVersion` 或实验性 SSR streaming。依赖在基座实现时写入精确 lockfile，不能以浮动 `latest` 作为可重复构建依据。

为了不改变已批准的后端安全和流式语义，Nuxt 不新增业务 API 真源：`/api/v1` 仍由 Go 负责，浏览器生成请求通过入口代理直接到 Go。SSR 可以输出公共页面和中性应用外壳；任何按用户变化的请求都必须透传 Cookie、遵守 `no-store`，且不得进入跨请求缓存。生成、访客承接和复习 attempt 仍在 hydrate 后由浏览器状态机管理。

## 用户决定

`CONFIRMED`：用户指定“单页面用 Vue，SSR 用 Nuxt”，并选择本项目使用最新稳定版 Nuxt + TypeScript + Vite。由此确认 Nuxt SSR 为前端基座，并接受其 Nitro/Node 生产运行时；最新是稳定发行通道，不包括 nightly 或仍在开发的 Nuxt 5。

## 影响范围

- `technical/frontend.md` 将采用 Nuxt 4 的 `app/` 目录、文件路由、SSR/hydration、Vue composable/state、Vite 构建与 Nitro 部署设计。
- 生产拓扑从“Go 可直接托管前端静态文件”细化为“同源入口代理 + Nuxt Nitro + Go API”；DEC-028 的同源 Cookie/CSRF 结论不变，DEC-027 的 POST SSE 和 Go 单副本边界不变。
- 前端实现必须验证 SSR 无串用户缓存、hydrate 一致性、流式请求不经 Nitro 缓冲、入口代理 SSE 配置、直接访问页面路由和滚动发布时的旧 chunk 兼容性。
