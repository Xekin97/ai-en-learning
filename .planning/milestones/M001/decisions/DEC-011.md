# 管理员模型、组别、用户和密码权限

## 决策问题

需要明确 OpenRouter 凭据作用域、模型对用户的可见信息、组别配置失效时的行为、管理员对用户和学习内容的权限，以及初始管理员和密码重置流程。

## 已确认约束

- M001 只支持 OpenRouter。
- 每个权益组可获配多个模型，用户只能选择本组模型。
- 管理员可以查看用户学习内容并手动调整用户组。
- 账号使用用户名和密码，不收集邮箱，也没有邮件找回路径，见 `DEC-006`。
- 首版不要求管理员操作审计。

## 可选方向

### 凭据 A：全系统单一 API Key

- 收益：配置简单，避免重复存储密钥。
- 代价：所有模型共享同一凭据和提供方账户边界。
- 风险：密钥失效会同时影响全部模型。
- 适用条件：M001 单一 OpenRouter 账户。

### 凭据 B：每个模型独立 API Key

- 收益：可按模型隔离凭据和账户。
- 代价：密钥重复、轮换和管理复杂度增加。
- 风险：容易把模型与凭据配置错误关联。
- 适用条件：不同模型需要不同 OpenRouter 账户。

### 凭据 C：凭据配置与模型引用分离

- 收益：支持多凭据复用和轮换，长期演进性最好。
- 代价：引入额外实体、引用和失效状态。
- 风险：超出 M001 实际需要。
- 适用条件：近期就需要多账户或密钥池。

### 密码重置 A：管理员直接设置新密码

- 收益：无邮件服务时操作直接。
- 代价：管理员需要安全地把新密码交给用户。
- 风险：用户下次登录不被强制修改，临时密码可能长期保留。
- 适用条件：接受由管理员和用户线下协调。

### 密码重置 B/C：系统生成或管理员设置临时密码并强制修改

- 收益：降低临时密码长期使用风险。
- 代价：需要首次登录强制修改状态和额外页面流程。
- 风险：增加首版账号状态。
- 适用条件：需要更严格的恢复流程。

## 角色建议

`PROPOSED`：采用单一全局 API Key；密码重置采用管理员设置临时密码并强制用户首次登录修改。

## 用户决定

`CONFIRMED`：

1. 全系统使用一个 OpenRouter API Key，所有已配置模型共享该凭据。
2. 每个模型由管理员配置用户可见名称、可选说明、OpenRouter 模型 ID 和启用状态。
3. 普通用户只看到模型名称与说明，不看到 OpenRouter 原始模型 ID 或 API Key。
4. 管理员可以按用户名搜索账号、查看当前组、在正式账号/Pro/Plus 间调整、查看该用户复习库内容，并直接设置该用户的新密码。
5. 管理员直接设置的新密码不是强制临时密码，用户下次登录后不被要求立即修改。
6. 管理员重置密码后，该用户现有登录会话全部立即失效。
7. 已登录用户可以在提供当前密码后自行修改密码；修改成功后如何处理当前会话以外的会话由技术方案在不降低安全边界的前提下定义。
8. M001 不允许管理员冒充用户、删除用户账号、删除或修改用户学习内容。
9. 管理员配置固定四组的允许模型、允许长度、选词上限和滚动额度。
10. 若某组没有配置任何可用模型，属于有效但不可生成的配置；该组用户访问生成接口时收到明确配置错误，请求不调用模型也不占额度。
11. 若某组没有允许长度或额度为 0，同样禁止生成并显示对应配置错误。
12. 初始管理员账号通过部署配置创建；不提供公开管理员注册或普通账号升级为管理员的界面。

## 影响范围

- `DATA-*` 需要覆盖全局 OpenRouter 凭据配置、模型、组模型关联、管理员账号和密码重置后的会话失效状态。
- `CAP-*` 需要覆盖模型管理、组策略管理、用户搜索、换组、复习库查看、管理员重置密码和用户修改密码。
- `PAGE-*` 需要把普通用户与管理员信息严格分离，API Key 永不回显给普通用户。
- 后端必须保证没有模型/长度/额度的配置错误在调用 OpenRouter 前被拒绝且不占额度。
- 验收需覆盖模型停用、组无模型、额度为 0、管理员换组、密码重置会话失效和用户自行修改密码。
