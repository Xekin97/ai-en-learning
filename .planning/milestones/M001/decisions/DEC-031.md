# 前端接口数据、业务状态与渲染边界

## 决策问题

Nuxt 同时存在 SSR 首屏取数、hydrate 后客户端取数、普通 JSON mutation 和 POST SSE 流。若页面或组件直接读取 API DTO，后端字段、空值、枚举、分页、错误结构和流式协议会渗入渲染层，业务规则也会散落在模板与事件处理器中。M001 需要固定一条能长期扩展、可静态检查的数据依赖方向。

## 已确认约束

- 前端组的前端架构师与前端实现者都必须擅长业务逻辑与渲染解耦。
- 远端数据只允许经过以下两条链路之一：
  - `接口 DTO -> SSR 聚合/转换 -> 应用状态 -> 界面渲染`；
  - `接口 DTO -> 客户端数据转换层 -> 应用状态 -> 界面渲染`。
- 页面与组件不得直接使用原始接口数据渲染。
- 项目采用 Nuxt SSR；Go API 仍是业务真源，POST SSE 仍由浏览器通过同源入口直达 Go。
- API 成功 DTO 尚有 CR-005 待补齐，前端不得用推测字段绕过契约缺口。

## 可选方向

### 方向 A：页面直接调用接口并渲染 DTO

- 收益：初期代码最少。
- 代价：接口字段、业务判断、格式化和渲染强耦合；SSR 与客户端会形成两套实现。
- 风险：接口变动扩散到组件树，测试只能靠页面级 Mock，敏感字段更容易进入 DOM 或 Nuxt payload。

### 方向 B：只封装请求客户端，仍由组件解释返回值

- 收益：统一了鉴权、错误和请求头。
- 代价：只隔离了传输细节，没有隔离 DTO 与业务状态；模板仍承担数据转换。
- 风险：同一字段在不同页面被不一致地解释，本质问题仍然存在。

### 方向 C：传输、转换、应用状态和渲染分层

- 收益：SSR 与客户端共享纯转换语义；页面只消费稳定的状态和视图模型；DTO 变化集中在 schema 与 mapper；可以用静态依赖规则阻止越层。
- 代价：需要显式维护 DTO schema、mapper、应用模型、store 和 selector。
- 风险：若只写目录约定而没有自动检查，实施时仍可能回退为直接取数。

## 用户决定

`CONFIRMED`：采用方向 C，并把以下内容设为前端架构硬约束：

1. 服务端首访必须由 SSR 聚合器读取并校验 DTO，转换为可序列化的应用快照后写入状态；Nuxt payload 不得包含原始 DTO。
2. 客户端导航、查询、mutation 和流式事件必须先经过数据转换层，再由应用 action/reducer 更新状态。
3. 页面、布局和 Vue 组件不得导入 API client、DTO、DTO schema 或原始 SSE event，也不得在模板中解释后端枚举、空值、时间、分页和错误结构。
4. 状态管理只保存应用模型、请求状态和业务状态；渲染数据由 selector/presenter 从状态投影，组件只展示并发出用户意图。
5. 合同 Mock 必须从原始 DTO fixture 进入真实 schema、mapper 和 store 链路；直接构造视图模型仅限纯展示组件测试，不能代替接口契约测试。
6. 使用静态依赖检查、受限导入规则以及 mapper/store/selector/SSR 测试守住边界，不以类型断言或 `any` 绕过。

## 影响范围

- 重写 `technical/frontend.md` 的数据架构、目录、SSR、状态、Mock 和验证策略。
- `frontend-architect/base` 与 `frontend-implementer/base` 增加相同的不变量与交付要求。
- CR-005 的成功 DTO 不再只是 TypeScript 类型问题，也是 mapper、SSR 安全投影和合同 fixture 的实施前置条件。
- 后续接口变化优先由 transport schema 与 mapper 吸收；只有真实业务语义变化才继续影响应用状态与界面。
