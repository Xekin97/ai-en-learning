# 单仓库内前后端目录隔离并独立部署

## 决策问题

当前仓库根目录直接承载 Go 后端的 `cmd/`、`internal/`、`db/`、`assets/`、Go module 与 Docker 构建文件，尚未落地 Nuxt 前端。若继续在根目录叠加前端，代码所有权、构建上下文、镜像发布和未来迁移到 Kubernetes 的边界会混在一起。需要在前端实现前固定单仓库内的源码与部署单元边界。

## 已确认约束

- 继续使用一个代码仓库，不拆分前端仓库与后端仓库。
- `.planning/` 继续位于项目根目录，作为跨应用的产品与研发真源。
- 后端保持 Go 模块化单体，前端保持 Nuxt 4 SSR 单应用；两者不是同一进程，也不能构建成一个全栈应用镜像。
- 对浏览器继续提供同一公开 origin；`/api/v1/**` 直接路由到 Go，页面与 `/_nuxt/**` 路由到 Nuxt Nitro，生成 SSE 不经过 Nitro BFF。
- M001 使用目录内 Nginx 作为外部反向代理；未来迁移 Kubernetes 时由 Ingress 承接同一公开路径路由，不改变浏览器 API 契约。

## 用户决定

`CONFIRMED`：采用单仓库、前后端目录隔离和独立部署单元，目标顶层结构为：

```text
project/
  .planning/
  backend/
  frontend/
  nginx/
  dockerfile-or-root-deployment-entry
  README.md
```

并确认：

1. 现有 Go 代码、迁移、查询、词表资产和后端构建配置整体归入 `backend/`。
2. Nuxt 工程全部归入 `frontend/`，拥有自己的依赖、构建、运行和单应用镜像边界。
3. `backend/` 与 `frontend/` 必须各自具备可独立构建、测试、启动、探活和部署的设计；根级部署入口不得把二者合并为单一运行进程或单一应用镜像。
4. `nginx/` 保存 M001 同源入口配置并作为独立 edge 单元；本地/单机部署由它反向代理，Kubernetes 部署可用 Ingress 替换它。
5. 根级保留统一部署入口与 README。用户原始结构中的 `dockerfile` 表示 Docker/部署入口；具体落为各应用 `Dockerfile` 加根级 `compose.yaml`，还是附加根级入口文件，由技术修订在保持独立镜像边界的前提下确定。

## 影响范围

- 已批准 [`technical/backend.md`](../technical/backend.md) 的建议目录、构建上下文、部署拓扑、配置路径、迁移/维护命令和回滚说明需要修订。
- [`technical/frontend.md`](../technical/frontend.md) 需要明确其所有目录均相对于 `frontend/`，补充独立 Nitro 镜像、探活、环境配置和 Nginx/Ingress 边界。
- 当前根目录的 Go 实现需要在后续实现角色中迁移到 `backend/`；本技术设计决策本身不移动代码。
- Docker/Compose、CI 工作目录、sqlc/Go/Nuxt 命令、Nginx SSE 配置、README 和验证脚本均需同步。
- 数据库逻辑模型、HTTP `/api/v1` 契约、同源 Cookie/CSRF、AI 行为和产品页面范围不变。
