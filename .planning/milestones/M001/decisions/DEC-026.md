# 后端运行时、框架与数据访问基线

## 决策问题

当前仓库没有既有后端代码或团队技术栈约束。M001 需要确定后端运行时、HTTP 框架和 PostgreSQL 访问方式，后续才能稳定设计模块边界、流式协议、认证会话、Markdown API 契约、测试和容器构建。本决策不选择云厂商或部署地区。

## 已确认约束

- 采用 `consumer-ai-web@1.0.0` Profile，从模块化单体和最小基础设施开始；M001 不预设微服务、Redis、消息队列或分布式事务。
- [`DEC-025`](./DEC-025.md) 与 [`technical/database.md`](../technical/database.md) 已确认 PostgreSQL 18、`wordweave` schema、原始 SQL 迁移是数据库契约真源，OpenRouter 调用不得占用数据库事务。
- CAP-008/009 要求一个请求内完成长耗时流式传输、主动取消、被动断流识别和最终结构校验；CAP-002–005 要求服务端会话；所有生成输入必须在调用模型前严格拒绝未知字段与越权值。
- 需要让未来前端使用稳定的 JSON/流式契约；M001 只维护 Markdown API 契约，不要求 OpenAPI。
- 当前官方状态：Node.js 24 是 LTS 版本；Fastify 5 是受支持主线并提供 JSON Schema 校验与插件封装；NestJS 当前主线为 12；Go 1.26 仍在官方支持窗口。[Node.js Releases](https://nodejs.org/en/about/previous-releases) · [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/) · [NestJS Migration Guide](https://docs.nestjs.com/migration-guide) · [Go Release History](https://go.dev/doc/devel/release)

## 可选方向

### 方向 A：Node.js 24 LTS + TypeScript + Fastify 5 + Kysely/node-postgres

- 结构：ESM TypeScript 模块化单体；Fastify 插件对应领域模块；Kysely 提供类型安全查询组合，底层使用 `pg` 连接池；数据库迁移继续使用 DBA 批准的原始 SQL，不交给查询构建器生成。
- 收益：前后端可共用 TypeScript 概念和契约类型；Node 原生流与 `AbortController` 适合 OpenRouter 转发和取消；Fastify 以 JSON Schema 做请求/响应校验并具有模块封装机制；Kysely 保留 SQL 可见性和复杂查询逃生口。[Fastify Validation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) · [Fastify Encapsulation](https://fastify.dev/docs/latest/Reference/Encapsulation/) · [Kysely Introduction](https://www.kysely.dev/docs/intro)
- 代价：需要团队自行坚持模块边界，不由重型框架强制；流式状态机、依赖组装和事务辅助器需要项目内明确规范。
- 风险：Node 进程不适合在内存中保存可恢复任务状态，因此 M001 必须维持“刷新不可恢复”，把正式状态与幂等终态落到 PostgreSQL；连接池与长流连接需要分别限流。
- 适用条件：优先快速实现消费级 Web、保持一个语言生态，并希望框架足够轻而不牺牲严格校验。

### 方向 B：Node.js 24 LTS + TypeScript + NestJS 12（Fastify Adapter）+ Kysely/node-postgres

- 结构：Nest 模块、Provider、Guard 与 Exception Filter 组织模块化单体；HTTP 层使用官方 Fastify Adapter；数据库边界与方向 A 相同。
- 收益：依赖注入、模块、权限 Guard 和测试装配约定完整，随着团队扩大更容易保持统一结构；Nest 官方支持 Fastify 作为底层 HTTP 平台。[NestJS Fastify](https://docs.nestjs.com/techniques/performance)
- 代价：装饰器、DI 容器、适配层和框架生命周期增加样板与调试层级；本产品 M001 的模块数量尚不足以天然抵消这些成本。
- 风险：流式响应和底层连接关闭检测最终仍需下沉 Fastify/Node API，Nest 抽象不能消除这部分复杂度；Nest 12 的 ESM 与工具链约束需要统一锁定。
- 适用条件：团队已熟悉 Nest，或明确偏好框架强制的模块与依赖注入约定。

### 方向 C：Go 1.26 当前补丁 + `net/http`/Chi + pgx/sqlc

- 结构：编译型 Go 模块化单体；标准 HTTP 流与 context 取消；pgx 连接池；sqlc 从手写 SQL 生成类型安全访问代码。
- 收益：运行时资源可预测、取消传播与并发模型直接、单二进制部署简单；手写 SQL 与 DBA 的 schema 真源高度一致。
- 代价：前后端使用不同语言；AI 结构流解析、界面契约类型复用和产品快速迭代需要更多重复定义。
- 风险：团队若主要熟悉 TypeScript，首版交付速度与后续维护成本可能高于其运行效率收益；当前产品没有并发或性能 SLA 证明必须为此换语言。
- 适用条件：团队已有 Go/pgx/sqlc 生产经验，或明确把低资源部署和编译型后端置于全栈开发效率之上。

## 角色建议

`PROPOSED`：选择方向 A。

理由：当前最复杂的后端问题是受约束 AI 流式状态机、事务终态和严格输入契约，而不是大型组织协作或极端吞吐。Fastify 的 JSON Schema 与封装足以支撑清晰模块；TypeScript 降低前后端契约重复；Kysely/`pg` 既提供类型辅助，也不会夺走原始 SQL 迁移的控制权。与 NestJS 相比它减少一层框架抽象；与 Go 相比，在没有性能 SLA 的情况下更利于首版快速闭环。

若选择 A，后续技术设计仍会明确：

1. 模块化单体边界和只允许单向依赖的规则；
2. 严格拒绝未知字段的 JSON Schema 配置，而不是静默移除字段；
3. 原始 SQL 迁移、Kysely 查询类型和 PostgreSQL 事务客户端的职责分离；
4. 流式协议、显式取消和被动断流的唯一状态转换；
5. 平台无关的 OCI 容器和同源部署，不在本决定中绑定云厂商。

## 用户决定

`CONFIRMED`：用户选择方向 C。M001 后端采用 Go 1.26 当前安全补丁版本、`net/http` + Chi、pgx v5 与 sqlc；保持模块化单体，原始 SQL 迁移继续作为数据库 schema 真源，不绑定云厂商或部署地区。
