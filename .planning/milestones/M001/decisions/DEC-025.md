# M001 主数据库选型

## 决策问题

M001 没有现成代码、数据库或部署平台，需要先确定主数据库引擎，才能继续设计字段类型、约束、索引、事务、迁移与备份恢复。本决策只选择数据库，不绑定后端语言、ORM、云厂商或具体部署地区。

## 已确认约束

- 产品是单一公众消费 Web 应用，M001 从模块化单体与单一关系型数据库开始评估。
- DATA-003 至 DATA-018 包含账号、会话、组策略、计量事件、生成批次、复习会话、复习结果与语言偏好，存在明确所有权、关系和级联删除要求。
- CAP-008/009 要求同一账号或访客同一时刻只有一个活跃生成，并要求额度占用、退款和结果状态保持一致。
- CAP-022 要求同一批次最多存在一个未完成单批次复习会话，同时允许日期范围会话独立共存。
- 用户名需要忽略大小写全局唯一；学习库需要按所有者、保存时间和精确目标词条查询。
- 用户规模、并发量、部署平台、可用性目标和成本上限尚未确定；M001 不应基于未知规模预先引入分库分表或多数据库架构。
- 来源：已批准的 `overview.md`、`data-assets.md`、`abilities.md`、`ai-behavior.md` 与 `consumer-ai-web@1.0.0` Profile。

## 可选方向

### 方向 A：PostgreSQL 单主关系数据库

- 收益：事务、行级锁、检查约束、部分唯一索引、表达式索引和 JSON 能力适合额度结算、活跃请求互斥、未完成会话唯一性与结构化 AI 元数据；主流托管平台支持广泛。
- 代价：本地和部署环境需要运行独立数据库服务，并建立迁移、备份和连接池配置。
- 风险：若没有限制连接数和定期维护，低配部署可能出现连接耗尽或表膨胀；可通过连接池、监控和常规维护控制。
- 适用条件：希望 M001 保持单库简单结构，同时把关键并发和一致性规则落到数据库层。

### 方向 B：MySQL 单主关系数据库

- 收益：托管选择广、团队熟悉度通常较高，也能覆盖核心关系、事务和索引需求。
- 代价：条件唯一性、大小写归一化和部分索引等规则需要更多生成列、辅助字段或应用层配合，数据库契约更绕。
- 风险：字符集与排序规则选择不当会让用户名、词条和多语言文本比较产生隐性差异。
- 适用条件：已有明确 MySQL 运维基础或部署平台只优先支持 MySQL。

### 方向 C：SQLite 单文件数据库

- 收益：本地开发和单机部署最轻，不需要独立数据库服务。
- 代价：写并发串行化、在线运维和高可用能力较弱；生成计量、管理员配置和学习写入并发增长时更容易形成写锁竞争。
- 风险：产品一旦需要多实例部署或更稳定的在线备份，通常需要迁移到服务型数据库。
- 适用条件：明确只做单机、低并发、短生命周期演示，而不是面向公众持续运行的 Web 产品。

## 角色建议

`PROPOSED`：选择方向 A，采用 PostgreSQL 作为 M001 唯一主数据库。它能在不引入额外基础设施复杂度的前提下，将最关键的唯一性、事务和并发规则直接编码为可验证的数据库约束；相比 SQLite 更适合公众 Web，相比 MySQL 对本产品的条件唯一性表达更直接。

## 用户决定

`CONFIRMED`：选择方向 A，M001 采用 PostgreSQL 作为唯一主数据库。当前不绑定后端语言、ORM、云厂商或部署地区；具体 PostgreSQL 最低版本、扩展使用和运维基线由数据库设计在官方支持范围内确定。
