# 用户详情“可用次数”缺少真实额度读取契约

## 发现的问题

PAGE-103 详情显示“可用次数”，但生产页面直接渲染 `common.unlimited`。现行 API-103 用户详情只提供身份、方案、创建日期和学习批次数，不能给出该用户当前滚动窗口的剩余次数。原型的“无限”是演示数据，不能成为所有账号的业务结论。

## 证据与来源

- [批准设计记录](../reviews/uiux-design-cr031-cr032-revision.md)；`design/prototype/app.js` 的 `renderAdminUserDetail`：`detailItem('可用次数', '不限')`。英文精确标签为 `Available`，与生产本地化 label 的措辞差异也须按原型核对。
- `frontend/app/pages/admin/users/[userId]/index.vue`：可用次数值为 `$t('common.unlimited')`。
- [API-103](../technical/api/index.md) GET 用户详情、换组返回的 AdminUserDetailDto，以及 `frontend/app/infrastructure/http/schemas/admin.ts`：没有 quota/remaining 投影。
- API-102 只有组策略 `rolling_24h_limit`，无法知道目标用户已用量；API-004 的额度只属于当前生成主体，不能拿管理员的额度冒充目标用户额度。
- [产品数据](../product/data-assets.md) DATA-006/009；[页面](../product/pages/index.md) PAGE-103；CAP-104/105。换组重置现行额度，但组上限不等于一般时刻的剩余额度。

## 建议变更

PROPOSED：用户授权后，由 backend-alex 明确最小只读额度汇总契约、权限及一致性，前端随后实现严格 schema → mapper → 应用状态 → 详情 presenter。具体字段/路径由后端契约决定，本 CR 不预造 DTO。

需覆盖有限剩余、耗尽、零上限、无限、窗口到期、换组重置及管理员不适用；不得返回计量事件明细、成本、敏感令牌，也不得新增额度修改功能。后端确认是否可复用现有计量读取而无需 schema 变更。读取是当时快照，不承诺客户端实时倒计数或自动轮询。

## 不变更的影响

有限账号会被错误显示为不限；既有换组额度行为无法在详情真实验收。不能以视觉比对或纯前端假数据关闭此项。删除该行、改成“方案上限”或永久占位均改变已批准语义，须另行确认，不能由前端自行替代。

## 路由建议

- 责任阶段：technical-design；建议责任角色 backend-architect/base（backend-alex），然后 frontend-architect/base 同步；实施与独立测试跟随契约。
- 阻塞范围：额度字段与 PAGE-103 完整验收；不阻塞 CR-029–032 的独立技术方案编写。
- 用户决定：是否允许超出 TRANSITION-M001-060 的仅前端范围，补齐最小后端只读额度契约；或暂缓并保留明确未关闭缺口。
- 不自动返回产品/UI；若后端确认所需汇总超出现有产品可见权限，必须再提出明确的范围决策，不能顺势扩大到事件报表。
