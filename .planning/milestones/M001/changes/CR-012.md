# 账号注销缺少明确且默认未勾选的二次确认控件

## 发现的问题

PAGE-009 注销危险区只有当前密码输入和永久删除按钮，点击后使用浏览器确认对话框；页面没有已批准的独立二次确认 checkbox。

后端正确要求 `confirmed:true`，并且账号、学习内容与会话级联删除已通过验证。但当前前端在用户只输入密码后自行发送该确认值，无法证明用户完成了产品定义的第二个明确动作。

## 证据与来源

- 产品真源：`product/abilities.md` CAP-005、`product/pages/index.md` PAGE-009。
- 设计真源：`design/interactions.md` §账号设置、`design/responsive-accessibility.md` 删除确认规则。
- 复现：已登录学习者进入 `/account`，检查 `.danger-zone input[type="checkbox"]`。
- 实际结果：checkbox 数量为 0；预期为 1，且初始不得勾选。
- 自动化证据：[`reverification-results.json`](../verification/evidence/reverification-results.json) 与 [`revision-e2e.mjs`](../verification/evidence/revision-e2e.mjs)。

## 建议变更

1. 在注销危险区增加可访问名称明确的 checkbox，初始与每次成功/失败后的安全状态均为未勾选。
2. 当前密码非空且 checkbox 已勾选时才允许发起注销；前端请求中的 `confirmed` 必须来自该控件状态。
3. 保留现有后端校验和级联删除语义；浏览器确认对话框可移除，或仅作为附加保护，不能替代页面内明确确认。
4. 增加键盘、读屏、取消、密码错误和成功注销浏览器回归。

## 不变更的影响

不可逆账号与学习数据删除缺少批准的第二确认动作，PAGE-009 和 CAP-005 无法通过破坏性操作验收。

## 解决记录

- 2026-09-02 由 `frontend-claire` 完成修订：PAGE-009 注销危险区增加带明确可访问名称的原生 checkbox，初始未勾选；当前密码非空且 checkbox 已勾选时，永久删除按钮才可用。
- 删除请求的 `confirmed` 值现在从页面 checkbox 传入 account store 和 API port，不再由 store 固定写入；浏览器确认对话框已移除，避免用通用对话框替代批准的页面内确认动作。
- 密码校验失败后 checkbox 自动恢复为未勾选，必须再次确认才能重试；成功后同样先清空本地密码和确认状态，再离开账号页面。
- 浏览器回归覆盖初始状态、键盘 Space 勾选、未勾选时无写操作、错误密码、失败后安全复位、成功注销及两次请求体 `confirmed:true`；桌面/移动端均通过，全页面 Axe 扫描无 serious/critical 发现。
- 结论：建议项 1–4 已实现，CR-012 关闭；最终破坏性操作验收仍由 verification 角色独立确认。
- 2026-09-02 由 `qa-quinn` 在全新组合环境独立复验：checkbox 默认未勾选且可由 Space 操作；密码错误后恢复安全状态；两次请求的 `confirmed:true` 均来自显式控件；成功注销后当前及其他会话、身份和学习所有权全部失效。CR-012 验收 PASS。
