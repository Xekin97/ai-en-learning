# 成功改密204缺少既有契约的no-store响应头

## 发现的问题

QA081真实改密成功返回204、0字节且无Content-Type，业务和会话行为正确，但没有Cache-Control: no-store。这是既有API缓存约定的实现偏差，非新产品要求，未发现实际凭据/正文泄露。后端候选本轮未改，不能归因为DEV080新增回归。

## 证据与来源

- 上游：[HTTP API v1.4](../technical/api/index.md) §1.3/1.6/API-003；[QA081报告](../verification/cr037-081-report.md) QA081-02。
- 追踪：CAP-004，PAGE-009，DATA-003/004，API-003。
- 两个独立合成账号重复验证：[API结果](../verification/evidence/cr037-081/account-api-results.json)、[真实响应头](../verification/evidence/cr037-081/residual-proof-observations.json)。
- 复现：学习者会话携带CSRF/同源头，PUT /api/v1/me/password，提交正确当前密码及两份相同合法新密码；查看204响应头。
- 只读定位：backend/internal/httpapi/response.go:64 writeNoContent未设置no-store；JSON/Problem helper已设置。代理后实际响应也无该字段。
- 候选后端sha256:e8c4ee91a7c3265cda8c496ccc8fb485328d95b6c1662eaf2502011ce5d005a5。

## 建议变更

PROPOSED：backend-ethan按现有契约为适用的204响应补齐no-store，保持无响应体和无Content-Type。不更改API字段/状态、密码策略、会话事务或数据库。

共享writeNoContent用于退出、改密、注销及部分学习/管理动作，应由实现角色梳理消费者并补有边界的回归；独立QA随后验证实际代理响应。不可恢复操作只使用可重建合成数据，不动现有UAT账号或学习内容。

## 不变更的影响

接口实现继续偏离已批准缓存契约。当前是空204的较低风险缺口，没有证明响应泄露或业务失败；不能夸大成已发生的安全事故。
