# 管理端 Users、Plans、Models 未逐字逐态对齐批准原型

## 发现的问题

PAGE-101～103 使用了与批准原型含义接近但并不相同的文案和展示规则。Users 搜索结果的日期/方案展示、Plans 的副标题与 Guest 名称、Models 的副标题、状态、操作、引用说明和 Add/Edit dialog 均被用户 UAT 判定为不一致。

## 证据与来源

- 上游产物：`design/prototype/app.js`、`design/prototype/i18n.js`、`design/theme.css`、`design/interactions.md`。
- 相关编号：PAGE-101、PAGE-102、PAGE-103；CAP-101～104；DATA-003、DATA-006、DATA-008。
- 当前差异示例：生产英文使用 `Manage the API key… / Set… / Visitor / Enabled / Edit model / Used by … groups`，批准原型使用 `Manage your API key… / Choose… / Guest / Active / Edit` 及原型定义的方案引用文本。
- Users presenter 对无 plan 值直接展示 `—`，且通用 `dateStyle=medium` 不能保证得到原型的日期表达。
- 用户 UAT 与静态复核记录：`verification/evidence/user-uat-visual-regressions-2026-09-04.md`。

## 建议变更

1. 以批准原型实际渲染结果为唯一 copy/结构基线，修正 PAGE-101～103 的中英文文案；不得自行采用“意思一样”的替代词。
2. Users 结果行逐项匹配原型的角色、日期、方案标签/值、状态和操作；日期格式在 SSR 与客户端必须一致。
3. `visitor` 方案在英文界面显示 `Guest`。不得把管理员的 `plan_code=null` 误标为 Guest；如果运行数据包含合同外的 visitor user，先记录其响应来源并在 mapper/presenter 层显式区分。
4. Models 列表和 Add/Edit dialog 同时修正可见文案、字段顺序、helper、switch、notice、按钮和间距，不只替换标题。
5. Plans 修正副标题、四个身份标签、字段标题间距和保存按钮，并保留既有权限/保存行为。
6. 增加 `zh-CN` / `en-US` 下实际页与原型的完整可见文本快照和关键区域截图对照。

## 验收条件

- PAGE-101～103 的可见静态文案与批准原型逐字一致，动态数量只替换变量部分。
- Users 日期和 Current plan 区域的层级、格式及文案与原型一致；visitor 显示 Guest，admin null 不伪装成 Guest。
- Models 的 Active/Inactive、Edit、方案引用以及 Add/Edit 两个 dialog 与原型一致。
- Plans 的副标题、Guest 身份和保存操作与原型一致。
- 中英文 × 390/1440px 无溢出，目标状态 Axe serious/critical 为 0。

## 不变更的影响

管理员会持续看到一套与已批准设计不同的术语和层级，最终 UAT 无法通过；宽松的“近义文案”测试还会继续产生假阳性。
