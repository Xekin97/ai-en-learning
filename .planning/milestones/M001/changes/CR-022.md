# PAGE-103 加载更多与 720px 列表未落实批准设计

## 发现的问题

PAGE-103 列表存在两类实现偏差：

1. 点击“加载更多”后，全局 `loading` 状态把已显示的 20 行卸载并替换成 3 行初始搜索骨架；请求完成后虽然正确追加到 25 行，但焦点落到 `body`。
2. 在 720px 下，实际列表仍保留紧凑四列桌面布局，“查看”按钮只有约 71px；批准原型在同一宽度已改为身份、方案/状态、宽操作的纵向分组。

## 证据与来源

- `design/interactions.md`：加载更多只追加结果；返回与分页需要稳定焦点。
- `design/responsive-accessibility.md`：320–720px 结果身份独占首行，方案/状态次行，查看操作位于末行；不得横向滚动。
- 批准原型 720px：结果行约 670px，查看操作约 537px；实际同宽查看操作约 71px。
- 运行中 load-more：`rows=0`、`skeletons=3`、active element=`BODY`；完成后 25 行无重复，但 active element 仍为 `BODY`。
- 截图：`verification/evidence/screenshots/page103-list-audit/actual-loading-more.png`、`actual-results-720.png`、`prototype-results-720.png`。
- 证据：`verification/evidence/page103-list-audit.md`。

## 建议变更

1. 区分初次搜索 loading 与追加 loading；追加时保留已有结果，结果容器设置 `aria-busy`，按钮显示禁用/进度状态。
2. 追加完成后采用批准设计允许的稳定策略：焦点保留在仍存在的加载按钮，或移动到第一个新增结果的“查看”；若没有下一页，必须采用后者或等价可感知目标。
3. 将批准原型的 PAGE-103 320–720px 结果行规则同步到生产 CSS，不要把关键断点缩到 560px。
4. 增加延迟 cursor 请求下的 DOM/focus 回归，并在 320、390、720、1440px 做 actual/prototype 几何对照。

## 不变更的影响

分页时管理员失去上下文与键盘位置，辅助技术用户无法判断结果是在追加还是重新搜索；平板/大手机上的列表明显偏离批准设计并压缩用户名与操作空间。
