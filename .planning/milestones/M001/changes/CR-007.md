# 将现有根级后端改为独立 backend 应用并重做统一入口部署契约

## 发现的问题

现有仓库根目录以 Go 后端为应用根：`go.mod`、`cmd/`、`internal/`、`db/`、`assets/`、`Dockerfile` 与 `compose.yaml` 均位于顶层；已批准后端文档也把这些目录视为仓库根路径。用户在 Nuxt 前端落地前确认改为单仓库内 `backend/`、`frontend/`、`nginx/` 三个独立部署边界。

这一调整同时影响后端构建上下文、迁移与维护命令、Nuxt 私有上游地址、Nginx 路由、Docker/Compose、CI 工作目录和回滚流程，不能只由前端文档局部覆盖，也不能在实现阶段直接移动文件而不先修订技术真源。

## 证据与来源

- 用户确认：[`DEC-033`](../decisions/DEC-033.md)。
- 当前实现：仓库根目录直接存在 `go.mod`、`cmd/`、`internal/`、`db/`、`assets/`、`Dockerfile`、`compose.yaml`。
- 当前后端设计：[`backend.md`](../technical/backend.md) 第 3.2、11 节仍以根级 Go 工程和笼统 edge 为前提。
- 当前前端设计：[`frontend.md`](../technical/frontend.md) 已定义 Nuxt/Nitro 与同源入口，但尚未绑定新的仓库根、独立镜像和 Nginx/Ingress 交付结构。
- 相关决策：DEC-027、DEC-028、DEC-030、DEC-031、DEC-033。

## 建议变更

1. 由 `backend-architect/base` 先修订跨应用仓库与部署真源：
   - `backend/` 作为完整 Go module/build context，包含后端 Dockerfile、迁移、sqlc、词表和维护命令；
   - `frontend/` 作为完整 Nuxt package/build context，独立产出 Nitro Node 镜像；
   - `nginx/` 保存 Nginx 镜像/配置、SSE 禁缓冲、真实来源头与同源路径分发规则；
   - 根级使用编排清单和 README 组合三个应用单元，不生产“前后端合一”镜像。
2. 固定公开路由：`/api/v1/**` 与必要健康路径直达 backend，页面/`/_nuxt/**` 到 frontend；`/internal/metrics` 不暴露公网。SSR 从私网访问 backend，浏览器仍访问同源 `/api/v1`。
3. 明确 Nginx 与未来 Kubernetes Ingress 使用相同路径契约；Ingress 替换 edge 层，而不是改变前后端应用或引入 Nitro BFF。
4. 后端技术修订获批后，返回 `frontend-architect/base` 更新 Nuxt 根目录、容器、运行配置、SSR 上游、探活、CI 和部署验证。
5. 最后由实现角色按批准后的迁移清单移动现有后端文件并创建前端/Nginx 基座；技术设计阶段不直接改代码路径。

## 不变更的影响

- Nuxt 落地后再移动 Go 根目录会同时放大 import/build context、Compose、CI、文档与缓存失效范围。
- 根级共享 Docker 构建会模糊单应用发布边界，使后续 Kubernetes Deployment/Service/Ingress 拆分需要二次重构。
- 若 Nginx、Nitro 与 Go 都尝试代理 API，SSE 缓冲、Cookie/CSRF origin 和断连取消语义可能发生漂移。

## 路由建议

- 应返回的责任阶段：保持 `technical-design`，先激活 `backend-architect/base`（`backend-alex`），再返回 `frontend-architect/base`（`frontend-bob`）。
- 是否阻塞当前工作：阻塞前端最终技术设计和后续目录/部署实现；不影响已确认产品、UI/UX、数据库模型与 API 业务字段。
- 需要用户决定的问题：高层目录与独立部署边界已由 DEC-033 确认；根级 Docker 编排文件的具体命名与组织由技术角色提出最小方案，随修订一并验收。
