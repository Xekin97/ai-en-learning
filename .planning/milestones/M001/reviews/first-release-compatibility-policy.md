# 首版不承担旧版兼容；以后由用户专项决定

## 用户已确认的决定

CONFIRMED：用户明确指出项目尚处第一版开发，要求“第一版不需要兼容任何功能”，并要求“以后出现任何兼容旧版的方案需要明显通知到我，我来决定兼容不兼容”。

本记录直接落实这次明确决定，不再次申请取消兼容的批准，也不把它解释成进入技术设计或其他阶段的请求。

## 当前范围覆盖

- M001 不承担此前开发候选、内部协议或测试快照的向后/向前兼容义务。开发期的 v2/v3 标记不代表已发布、必须支持的产品版本。
- 旧草稿/旧批次格式兼容、旧 API 兼容、跨旧镜像读写、旧版兼容回滚候选不再构成首版实现任务或验收门槛。
- 撤销 095 调查交付中“新增 v2 兼容修复回滚候选”的建议，不构建、不替换此类候选，不因不可修改的旧镜像缺陷阻塞首版。
- 此用户决定覆盖 CR-039 §8/C39-15、093/094/095 及其他早期产物中与之冲突的旧版本兼容要求。历史专业原件与测试事实原样保留，不能把旧测试失败改写成通过；这些兼容项后续应标为“用户取消范围 / 不适用”，而非要求返工。
- 不自动删除已有代码、历史镜像、测试数据或用户学习内容；不做数据库重置、迁移或部署。取消兼容义务不等于授权破坏现有资产。

## 所有后续旧版兼容方案的专项告知规则

本项目各阶段提出旧版兼容时，必须显著标注“旧版兼容，待用户决定”，并说明：

1. 要兼容什么旧版本、接口、数据或客户端，以及是否存在实际已发布用户/消费者；
2. 不兼容会影响谁、哪些数据或操作；
3. 兼容所需的实现、维护和测试成本，以及可不做兼容的替代方案；
4. 本次建议的边界和保留/退出期限。

未得到用户对该兼容事项的明确决定，不得默认纳入实现、测试或发布门禁；不得把一般的“批准方案”“下一步”或历史开发候选的存在当作未突出告知的兼容授权。后续确有需要也必须重新提出，由用户决定兼容或不兼容。

此规则针对旧版本兼容，不取消首版已明确支持的当前模型接入、客户端或当前前后端接口协作要求。
