# 返修保留完整旧稿，按段更新并反馈真实等待状态

## 发现的问题

用户在真实UAT3015反馈返修看似卡住，可能发生于审稿。当前公有状态仅 accepted/planning/composing/finalizing，fixed_edit/content_review/content_repair 一直保持 composing。Review完整接收审稿JSON后才返回，期间没有正文增量；15秒SSE心跳仅保活，不表达实际工作。publicAttempt首块会删除旧稿余下正文，再追加新稿，不能保留完整旧稿供阅读。

## 证据与来源

- [用户确认](../reviews/evidence/uat-feedback-097/user-confirmations.json)、[只读时序](../reviews/evidence/uat-feedback-097/real-run-timing.json)。
- 两次 mimo-v2.6-pro Pro 任务后端均 valid/repaired_passed，总计约134.66和200.42秒；首次审稿间隔分别47.87与15.86秒，修后审稿11.43与10.11秒。区间含编排开销，不能称为精确模型计算耗时。
- 无浏览器录像，后端成功不能排除客户端停滞；没有新增付费调用或文章质量测试。
- `backend/internal/generation/pipeline.go`、`backend/internal/ai/content_tasks.go`、`frontend/app/application/generation/reducer.ts`、`frontend/app/presentation/components/GenerationWorkspace.vue`。

## 建议变更

CONFIRMED：保留上一版完整正文；新稿有完整段落后逐段替换并短暂提示变化；审稿等待时轻量显示“正在完善内容”；不展示审稿详情、轮次、上限。词义用法/场景仍保持到最终完成。

后端先定义真实活动与版本边界信号，再交designer-tony按M002及UI11/UI12既有正式视觉制定可实施交互、双语文案和状态演示，然后frontend-bob接收。不能只改静态提示词、伪造模型进度百分比、用额外AI请求生成过程旁白，或以原型代替正式设计。

保持既有目标模型审稿、普通/付费权益、返修预算和达到上限定稿语义；既有技术故障/取消/最终valid整包及保存边界不变。缩短实际模型等待属于后续明确成本/质量取舍，当前展示修复不声称降低模型推理时长。

## 不变更的影响

真实审稿等待仍无法解释，旧稿消失重写会打断阅读，长任务容易被误认为失败或卡死。

## 路由建议

product-maya落实已确认交互边界 → backend-alex活动/流式契约 → designer-tony正式设计 → frontend-bob技术接收 → 前后端实施 → qa-quinn独立功能验证 → 真实UAT3015刷新。当前仅重开受影响范围；先检查门禁，不更改096历史接受记录。
