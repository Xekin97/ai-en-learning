# 后台运营配置按类别导入与导出

## 用户原始需求与已知边界

> “还有一个需求需要补充，不过这个需求偏技术类型，就是后台管理台除了用户之外，像模型配置、计划配置、道具配置这一类运营的相关配置，需要能分别实现配置的导入导出”

- `CONFIRMED / REQUEST-SCOPE`：本需求属于尚未收尾的 M003；管理员需要对运营配置按类别分别执行导入、导出。
- `CONFIRMED / EXCLUSION`：用户不属于导入导出范围。
- `CONFIRMED / USER-M003-CR313-CATEGORIES-20261015`：用户明确回复“预设短文和公告不需要导入导出”。本次范围为模型配置、计划配置、道具配置和成长规则（签到、等级、成就）；预设短文与公告排除。
- 当前只登记变更，不把“配置导出”解释为数据库备份，也不纳入用户账户、用户资产、库存实例、道具发放/使用流水、生成内容或其他业务历史。
- M003-UI-14 发音设计仍处于 `awaiting_user_review`，尚未审批；本 CR 不修改该设计、交接或 manifest，也不切换当前阶段。

## 现有配置入口与依赖事实

只读核对到现有管理员页面为 `admin/models`、`admin/plans`、`admin/growth`、`admin/presets`、`admin/notices`，均使用 admin middleware/layout；应用层目前按类别提供查询、保存、发布/上下架、影响预览等能力，未发现通用导入/导出端口。

| 现有类别 | 主要现状 | 已存在的依赖/语义 |
|---|---|---|
| 模型配置 | provider connection、provider model、启用状态和模型参数；保存受 configuration revision 约束 | 计划和预设引用模型；道具的模型试用效果可引用模型。读取连接只返回 `credentialConfigured` 与掩码提示，API Key 走独立凭据写入/读取路径 |
| 计划配置 | 分组优先级、额度、可用长度、可用模型、内容审阅/返修配置 | 引用模型；变更已有用户/试用影响预览与 accepted snapshot 语义 |
| 道具配置 | 道具类型、双语名称/说明、价格、激活期限及效果 | 效果可引用模型或计划；存在上下架、是否发放过、等级/成就引用与 revision 约束 |
| 成长规则 | 签到/成长设置、等级、成就及奖励 | 奖励可引用道具定义；设置含当前/待生效与 effective day，等级变更已有降级/受影响用户预览 |
| 预设配置（范围外） | 标题、模型、目标词、释义语言、场景、长度及预览模式 | 用户已明确不需要导入导出；其草稿、预览、发布版本、样例和用量均不进入本 CR |
| 公告（范围外） | 双语标题/Markdown、可见与提醒设置 | 用户已明确不需要导入导出 |

代码定位：`frontend/app/pages/admin/{models,plans,growth,presets,notices}.vue`、`frontend/app/application/admin/{configuration,items,growth,presets,notices}.ts`、`backend/internal/admin/{model_connections,model_providers,groups}.go`、`backend/internal/growth/{item_definitions,configuration}.go`。

上述事实意味着后续产品与技术设计必须明确类别边界、跨类别引用和目标环境缺失依赖的处理；不能直接把现有数据库行整包复制，也不能先假定一个无差别的通用迁移平台。

## 本轮精确问答与确认

类别、冲突策略与密钥处理均已获得用户明确选择：

1. `CONFIRMED / USER-M003-CR313-CATEGORIES-20261015`  
   问：全部现有运营配置（模型/计划/道具/成长规则/预设配置/公告），还是仅模型、计划、道具？  
   答：“预设短文和公告不需要导入导出。”协调方已复述为模型、计划、道具和成长规则（签到、等级、成就），排除预设及公告。
2. `CONFIRMED / USER-M003-CR313-REPLACE-20261015`  
   问：预览后合并更新并保留缺失项、仅新增且跳过已有项，还是替换所选类别的全部配置？  
   答：选择“替换所选类别的全部配置”。该选择只作用于管理员本次选中的运营配置类别；不扩展到用户资产、库存实例、发放/使用流水、生成内容或其他历史。
3. `CONFIRMED / USER-M003-CR313-ENCRYPTED-KEY-20261015`  
   问：默认不导出 Key、目标环境保留/补填，还是提供可选加密导出？  
   答：选择“提供显式选项，将密钥随配置一起加密导出”。这是管理员主动选择的可选路径；加密格式、密钥托管、口令/密钥交换、恢复与失败行为留待后续产品及技术设计，本 CR 不作方案。

当前确认的是产品行为方向，不固化文件格式、API、对象身份映射、执行顺序或验收标准。技术阶段仍需回答版本/schema 标识、稳定引用映射、依赖排序、revision 冲突、全量替换的预览/确认及部分失败原子边界，以及可选密钥导出的安全合同；这些是后续设计事项，不是本次已确认实现方案。

## 建议路由与恢复点

`product-maya` 先按已确认类别边界、所选类别全量替换及显式可选的密钥加密导出，定义数据边界和可观察结果；再由相关管理员 UI 设计明确各类别的导出入口、导入替换预览、依赖/失败反馈及密钥选项；随后由 backend/frontend 技术角色设计最小可实施合同并进入各自门禁。若范围包含多类别依赖，优先复用现有 revision 与影响预览语义，不先建设通用迁移平台。

恢复时从本文件继续。CR-313 保持 `open`；当前 M003 阶段、M003-UI-14 待审状态及既有 UAT/验收记录均不因本次登记改变。
