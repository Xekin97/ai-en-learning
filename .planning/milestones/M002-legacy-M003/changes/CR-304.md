# generation_busy 响应缺少契约要求的重试秒数

## 发现的问题

独立 QA 在真实 Go HTTP、独占单槽准入环境中保持一个已受理生成请求，再提交另一身份的生成请求。第二个请求正确返回 HTTP 503 `generation_busy`，响应头有 `Retry-After`，但 Problem 的 `context` 只有 `{"accepted":false}`，缺少 API-302 明确列为必填并要求与响应头一致的 `retry_after_seconds:int[1,600]`。

这会使前端无法按严格契约解析 busy 响应，因而不能可靠呈现保输入、到时仅解禁且不自动重 POST 的状态。

## 证据与来源

- 上游产物：[`technical/api/generation.md`](../technical/api/generation.md) 的“API-302 受理前忙碌拒绝（BE06）”；[`technical/frontend.md`](../technical/frontend.md) FE3-V13。
- 相关编号：API-302、FE3-V13、BE6-C03。
- 复现：本轮 disposable stack 配置 `GENERATION_MAX_IN_FLIGHT=1`；basic 请求收到 `generation.started` 后，Pro 请求 POST `/api/v1/generations/stream`。实际 HTTP 503、`Retry-After: 5`、`context={"accepted":false}`。
- 证据原件：[`verification/evidence/qa-m003-001/api-results.json`](../verification/evidence/qa-m003-001/api-results.json) 的 `checks.busy_503_before_acceptance`（完整QA脚本结束后落盘）；源码定位 `backend/internal/httpapi/generation_handlers.go` 的 busy 分支只写 `accepted`。

## 建议变更

- 用户已明确的要求及确认来源：TECH03 已批准 API-302，busy body 的 `retry_after_seconds` 与 Retry-After 必须一致；本项不新增业务规则。
- 在普通生成、用户预设生成、后台预览与模型探测共用的 busy Problem 中加入同一经过 1..600 限制的 `retry_after_seconds`，并保持 `accepted:false`、HTTP 503、no-store 与 Retry-After。
- 补定向契约检查，随后由 QA 以同一并发复现复验；不建立新容量平台或运行负载测试。

## 不变更的影响

严格前端 schema 会把本应可恢复的受理前 busy 误判为通用不可解析 503，用户不能获得合同允许的“本次未开始/保留输入/稍后可试”行为。

## 路由建议

- 应返回的责任阶段：implementation / backend-ethan；前端仅在修复后复验现有严格处理，不先放宽 schema。
- 是否阻塞当前工作：阻塞 FE3-V13 与本轮整体 PASS；不阻塞其他独立用例继续。
- 需要用户决定的问题：无。

## 解决记录

2026-10-12 独立定向复验 **PASS**。在仅供确定性复现的 `GENERATION_MAX_IN_FLIGHT=1` 一次性栈中，保持一个已受理请求后，第二请求得到 HTTP 503 `generation_busy`、`accepted:false`、无 SSE 事件；body `retry_after_seconds=5` 为合法整数并与 `Retry-After: 5` 一致，响应为 `no-store`。严格前端保留所选模型与两个词，cooldown 内禁用提交，到期解禁，POST 计数保持 1、没有自动重试，也没有退化为 contract violation。
