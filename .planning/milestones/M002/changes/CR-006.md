# 模型下架后已有卡的下架积分不能调整

## 问题与已批准期望

D2-51、CAP-215/217、AC-215 及 API-204/206 明确：下架积分由管理员调整且即时适用于尚未退换的已有卡；不按发卡金额冻结。禁止新引用 retired 模型不等于禁止维护已有下架卡金额。

当前已有模型卡在模型正式移除后，即使模型集合和其他参数都保持不变，只把 retirement_points 从 20 改为 35，后台仍返回 422 /effect/model_ids invalid_reference，不能实现这项运营规则。

## 复现与原件

1. 在隔离库创建含一个可用模型的模型卡，下架积分 20；兑换并启用。
2. 通过正式 removal-impact + DELETE 移除模型；用户 refund-preview 返回 eligible=true、points=20。
3. 管理员 GET 当前道具定义及 revision，原样回传全部字段，仅把 effect.retirement_points 改为 35。
4. PUT /api/v1/admin/growth/items/:id 返回 422，field=/effect/model_ids、code=invalid_reference；再 GET 仍为 20，revision 不变。

[完整道具检查 C06](../verification/evidence/qa2-001/cards-audit.json)、[检查脚本](../verification/evidence/qa2-001/cards-audit.mjs)、[最小重复复现](../verification/evidence/qa2-001/refund-config-repro.json)、[重现脚本](../verification/evidence/qa2-001/refund-config-repro.mjs)。重现明确 modelIdsUnchanged=true，没有尝试添加下架模型。

定向定位：backend/internal/growth/item_definitions.go 的 SaveDefinition 在更新时调用通用 validateDefinition；其模型校验统一要求 retired_at IS NULL，未区分新引用与当前既有引用。已有 activation_integration_test.go 通过 SQL 直接改 retirement_points，不能证明管理员正式保存路径可用。

## 处理范围与复验

backend-ethan 在既有 API/事务内区分新增引用与保留既有下架引用，确保当前定义可调整下架积分。保留正式下架、新增引用、卡类型、已发作用快照和 revision 安全校验；不以替换为另一个模型作为用户变通流程，不新增未讨论的接口或退款规则。

复验以真实管理员 API 完成：模型已下架、已有卡未退时调整积分成功；用户下一次预览立即为 35；原 20 分预览提交返回 preview_stale，重新确认只发 35 一次；已退卡不追补，已用/未用资格保持；新增卡仍拒绝引用 retired 模型。C06 后续退款断言因本缺陷尚未执行，不能沿旧开发证据自动关闭。

本项阻塞最终道具运营验收及 UAT，无需重选金额生效规则。当前 QA 不改实现或控制面，建议正式返回 implementation / backend-ethan。
