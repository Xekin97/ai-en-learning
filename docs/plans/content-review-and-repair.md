## 3. 普通与增强权益的行为

| 行为 | 普通权益 | 含 AI 内容审校的计划权益 |
|---|---|---|
| 首稿的场景、用词、文体与逻辑提示 | 应用共同提示优化 | 同左 |
| 写作前结构化规划（CONFIRMED） | 共同生成步骤，完整计划实际输入writer；正常规划＋首稿2次 | 同左；N0仍保留规划 |
| 固定实际编辑（CONFIRMED） | 不提供 | N>0一次，不占N/基础预算；规划＋首稿＋编辑＋首次审稿正常4次；N0关闭编辑/审稿/返修 |
| 目标词覆盖、格式、学习字段原生校验与原二次修正 | 保留 | 保留 |
| 独立 AI 内容审稿 | 不执行 | 执行 |
| 因明确内容问题进行整稿返修 | 不执行 | 在配置上限内执行 |
| 内容返修达到上限 | 不适用 | 最后原生有效稿正常定稿 |
| 保存与复习 | 保留原有有效结果规则 | 保存最后定稿及与其一致的学习字段 |

审稿重点是错义/词义前提缺失、为塞词添加无关事件、前后事实冲突、缺少动作或因果前提、明显偏题、文体或对话场景不成立。需要指出具体句子、问题及修正目标，不能仅因文风平淡、缺少高潮或结尾未解决一切而返修。

返修允许重写整篇，不限于追加结尾或修改释义；更改某个事实时必须同步修改依赖它的句子。每次新稿都重新通过原生校验，最终正文和学习字段必须来自同一版本。格式无效不因“内容次数用完”而变成可保存结果。

各付费计划的内容返修上限分别配置，允许整数 0～99，初始均为一次；0 沿现有开关联动表示关闭内容审校，开启范围为 1～99。这取代此前首版统一最多一次以及后续 1～2/1～3 的建议。不授权无限重试，也不将模型调用次数逐次扣成多次用户造文额度。内容审校技术故障已有有效稿时，按 CQ-12 提示未完成并交付最近有效稿，仍计一次业务生成；每次上游调用的用量分别记录。具体故障边界与结算不确定状态由责任角色设计，不能以降级交付掩盖结算未知或交付基础校验无效稿。

## 4. 产品需交付的管理台配置

在现有“计划管理”上扩展，不另建收费系统或另起一套计划模型。产品应明确下列事项，并为前后端给出可观察验收：

1. **权益字段**：AI 内容审稿开关、内容返修上限；基础漏词/格式校验是所有计划的基础能力，不能随付费开关关闭。管理界面清楚区分基础修正和内容返修。
2. **有效配置**：关闭时的次数含义；开启时是否允许只审不修；首版允许范围、默认值和无效值反馈。不得出现界面声称包含返修而配置实际不提供的组合。
3. **计划分配**：明确既有 visitor/basic/pro/plus 中的可配置范围与初始配置，不凭名称或排序在代码里猜“付费”；避免把升序优先级直接等同于权益集合。
4. **权益合并**：按既有基础计划、试用计划及有效计划计算规则继承内容权益。模型卡、额外次数卡是否授予内容权益要明确，不能因为有模型权限就隐含赠送。
5. **修改生效**：配置预览、保存、成功/失败反馈、并发编辑冲突及生效范围。进行中的请求须维持确定的权益与次数，不因管理员改配置或试用到期而在半途改变行为。
6. **用户端呈现**：遵守最新STREAM-FIRST/LIVE-TEXT，保留计划信息但不突出内部审稿/返修或上限轮次；文案不承诺零逻辑错误或必然高分。达到次数上限仍显示正常完成，不显示虚假的“审稿通过”。
7. **预设路径**：明确用户试用预设与后台预设预览各自适用的权益；公开已发布文章不能按每个阅读者再生成或审稿。

当前计划管理已经支持四个固定计划、影响预览、配置版本及冲突处理；优先复用这些能力。具体配置方案是本次产品角色的交付，不由研究文档擅自把建议登记成用户确认。

## 5. 交给后端设计的内容链路和流式体验

Q3-02已选A，后端按CR-302接收合同在保留权益边界内复核规划、writer、固定编辑、原生修正、内容审稿、限次返修、复审、定稿；具体schema、故障适配、版本身份和实现尚未批准，本文件不代替专业设计。普通请求与增强请求应共用原生校验及唯一结算能力，内容预算与技术修正预算分别计数，不能每次改稿重置全局上限。

最新LIVE-TEXT要求首稿和修订稿真实正文增量、可前进/回退/替换。共同规划先遵内容生成依赖，再投影已形成的真实词义/用法/场景；预览只呈现实际writer输入，不替代生成机制。临时本篇拟用义项与最终通用释义分开；研究英文规划不能声称已支持zh/ja摘要，需后端在同次规划中设计验证，不额外翻译调用。不得仅为填充等待界面额外调用模型，不展示模型私有推理，不将心跳、进度文案或半截 JSON 计作有用内容。

后端需要完整设计：何时确认请求受理；每类公开事件与完整性边界；哪些稿件可见；修改如何替换旧稿；取消和断连如何中止后续调用；上游打开失败、解析失败、审稿失败及原生修正失败如何终止；完成事件与保存资格如何对应；模型用量与业务额度如何各自结算。前端技术契约须依据后端定稿对齐，不在本方案固定事件名、版本字段或接收器结构。

观察首次有用内容时间、最长无新内容间隔、最终完成时间、内容版本变动和取消行为。Codex 离线样本没有测过实际 API 流式时延，不承诺秒数。项目尚处首版开发，遵守 [USER-COMPAT-001](../../.planning/milestones/M001/reviews/first-release-compatibility-policy.md)：不默认新增旧客户端协议兼容分支。

## 6. 提示改进和修稿统计

把已确认的共性问题沉淀到版本化首稿规则：用难词确定合适活动；词义需要的前提进入正文；相关不等于因果；人物归属、动作、物体和时间保持一致；对话后句回应前句；新增事件必须和当前任务有实际关系。沿用项目格式样例及输出契约，示例不能强迫所有体裁套同一种故事。

单次修稿意见只用于本次修稿，不自动修改全局 prompt。后续规则升级以固定样例和版本比较进行，避免把一篇文章的补丁不断堆入提示。

在现有生成记录/用量/诊断能力内增加最小必要事实，由后端决定落点：有效计划及权益快照、目标模型、提示版本、是否进入审稿、实际审稿次数、内容返修次数、具体触发类别、技术修正次数、最终交付原因。统计分母至少区分全部请求、增强请求、实际进入内容审稿的请求；文章去重数与调用次数分别报告。牵强和矛盾可同时出现，联合频率去重；复审再次报错但已到上限不算新增返修调用。

## 7. 现有实验能够支持的判断

最新固定批次为 20 例，全流程目标模型为 Codex Luna。进入审稿 15 例，5 例实际触发内容返修；其中牵强用词 4 例、明确前后矛盾 0 例、其他衔接问题 1 例。对应全部请求为 25% / 20% / 0% / 5%，审稿请求中的总返修率为 33.3%。

5 个返修案例按最新定稿规则得到 4 份定稿：2 份独立通过、2 份仍有重要问题；另 1 份因实验执行器误拦而中断。本批 6 例执行器中断不等于线上模型失败。最终可交付 14/20，其中独立通过 7 份、有重要缺陷 6 份、存在评价分歧 1 份；不能把交付率当质量通过率。

实验支持“具体问题可以通过反馈得到修复”的服务价值，也显示目标模型存在漏检。它采用了构思、必经编辑等环节，不能直接用以上比例预测已选A分层链路的效果或成本；没有消融证据证明可以无损删掉这两步。付费文案应承诺提供审稿与限次优化流程，不能承诺消除全部错误。

证据入口：[研究结论](../research/short-passage-quality.md)、[返修统计](../research/content-quality/acceptance-target-model-repair-statistics.json)、[原因复核](../research/content-quality/acceptance-target-model-repair-cause-coding.json)、[限次定稿重放](../research/content-quality/acceptance-target-model-delivery-policy.json)。保持这些冻结研究证据原样，不以实施后的测试覆盖原记录。
